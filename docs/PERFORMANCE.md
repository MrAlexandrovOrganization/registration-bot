# Локальный baseline производительности

`make benchmark` запускает Go benchmarks с GOMAXPROCS=1. Все HTTP endpoints
создаются через httptest; backend заменён fake-клиентом. Рабочие токены, Kafka,
PostgreSQL и Telegram не используются. Можно запускать независимо от backend.

Два разных измерения:

- **Webhook ingress**: настоящий HTTP/JSON, проверка секрета и ограниченная очередь
  с единственным consumer; fake Accept имеет заданную задержку 0/5/20 мс.
  Нет gRPC transport, реальной persistence, hints или отправки ответов. Измеряются
  closed-loop throughput и p95 клиентского HTTP запроса при 1/16 клиентах.
- **Sender cycle**: Claim → limiter → fake Telegram HTTP → Complete, последовательно,
  с искусственными 2 мс на каждый RPC и 0/70 мс на Telegram. Настоящий limiter
  20/с общий, 15/с broadcast, 1/с один private chat. Начальный слот прогревается.
  Измерение не включает discovery, очереди hints, Kafka и реальный backend.

Это короткие (3 секунды финальной выборки) компонентные baselines, а не
end-to-end нагрузочный тест и не production SLO. Экспорт OTel и запись логов
на диск не моделируются. Для устойчивого RPS нужны длительная нагрузка с
фиксированной частотой прихода, смесь сценариев и контроль роста очереди.

## Результат 2026-10-08

Apple M3 Pro, darwin/arm64, GOMAXPROCS=1:

| Webhook: задержка fake backend | Клиентов | Updates/с | p95, мс |
|---|---:|---:|---:|
| 0 мс | 1 | 22544 | 0,052 |
| 0 мс | 16 | 31894 | 1,08 |
| 5 мс | 1 | 172 | 6,00 |
| 5 мс | 16 | 179 | 90,23 |
| 20 мс | 1 | 47 | 21,49 |
| 20 мс | 16 | 48 | 336,0 |

Все запросы успешны. Строки с 0 мс — только накладные расходы frontend;
они не означают, что рабочий бот способен обработать 32 тысячи updates/с.
Один consumer сохраняет порядок: больше клиентов увеличивает ожидание в очереди,
но не превращает Accept в параллельный. Polling также обрабатывает updates по одному.

| Sender: сценарий | Сообщений/с |
|---|---:|
| Разные чаты, Telegram 0 мс | 19,99 |
| Разные чаты, Telegram 70 мс | 13,20 |
| Один чат, Telegram 70 мс | 1,00 |
| Broadcast, разные чаты, Telegram 0 мс | 15,00 |

Sender последователен; slow HTTP или ожидание лимита одного чата задерживает другие
сообщения. `/start` создаёт два ответа: даже при достаточном Accept RPS очередь
доставки может расти. Нужны отдельные SLO для durable приёма и видимого ответа.

## Прочтение trace 255d05126b00bdd81e41eb843a44686d

В локальном Jaeger на момент диагностики:

| Этап | Начало от update, мс | Длительность, мс |
|---|---:|---:|
| Backend Accept | 0,262 | 5,595 |
| Первая telegram.delivery | 8,037 | 71,635 |
| Вторая telegram.delivery | 1491,408 | 81,196 |

Промежуток после первой доставки до второй — 1411,736 мс. Limiter.Wait находится
**внутри** telegram.delivery, поэтому этот промежуток нельзя приписать ему по
этому trace. Claim выполняется **до** восстановления delivery traceparent, и его
RPC виден отдельным trace. Ближайший Claim перед второй доставкой занял 3,458 мс;
длинного backend RPC в найденных соседних traces нет. Существующая инструментация
не показывает время ожидания hints/recovery/выбора sender и не позволяет однозначно
восстановить причину паузы. Короткие baselines тоже не доказывают её причину.

Для следующего шага диагностики полезны время enqueue/dequeue hint, источник
fast-path/recovery/broadcast, результат Claim и отдельные spans limiter/Telegram HTTP.
При активном recovery возможны повторные hints: ID из очереди ещё не означает,
что backend уже разрешает захват. Не трактовать пустое место в Jaeger как CPU work.
